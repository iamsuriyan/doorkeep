# doorkeep technical design v1

Status: design for an empty repository. Everything below is a proposal; nothing is implemented. Where a trade-off exists, the recommendation and the reason are stated inline.

Working definitions used throughout:

- **Site**: a customer property registered on a doorkeep instance. Has a public `site_key` (`dk_pk_...`) embedded in HTML and a `secret` (`dk_sk_...`) used server-to-server.
- **Session nonce**: a one-time server-issued identifier that ties together snippet execution, optional challenge, token minting and backend verification.
- **Event**: the server-side record of one scored submission (bucketed features, risk, outcome, reasons). No raw signals are ever persisted.
- **Risk**: canonical score, integer 0-100, higher is more bot-like. A reCAPTCHA-compatible `score = 1 - risk/100` is derived at the verify boundary only.

## 1. Signal collection in the browser snippet

### 1.1 Design principles

1. **Neutral-when-absent.** No behaviour or environment signal may add risk simply because it is missing. Keyboard-only users, screen-reader users and touch users have no mouse trail; that is "no evidence", not "bot evidence". Risk is added for impossible or contradictory observations, and for absence combined with an automation marker.
2. **Privacy-browser profile detection comes first.** The snippet detects Firefox `resistFingerprinting` (RFP) / Tor Browser and Brave farbling using their own well-documented tells, and the server switches to a reduced rule set (`PROFILE_RFP`, `PROFILE_BRAVE`) in which fingerprint-consistency rules are disabled and only automation markers, behaviour and network signals apply. These profiles are informational reason codes, never penalties.
3. **Raw in transit only when the server needs semantics; hashed in transit when it does not.** Canvas, audio and font results leave the browser only as hashes/bitmasks. WebGL renderer, UA, screen geometry, timezone and languages are sent raw (the server must classify them) but are stored only as classes/buckets (section 6).
4. **Budget**: first-stage collection must finish in under 50 ms of main-thread time on a 2019-class Android phone; deferred-stage work (audio, fonts, rAF cadence) runs in `requestIdleCallback` and is sent with the final submit. Snippet target size: 12 KB gzipped, zero runtime dependencies, PoW worker loaded lazily.

Legend for "FP risk": Brave = Brave Shields default; RFP = Firefox with `privacy.resistFingerprinting` and Tor Browser; SR = screen readers / assistive tech. Cost is approximate main-thread time.

### 1.3 What must be hashed or bucketed before leaving the browser

Hashed in the browser: canvas image, audio buffer, font results (presence bitmask). Aggregated in the browser: all pointer coordinates, key timings and identities, scroll positions, element targets. Sent raw but stored only as class/bucket: UA, WebGL strings, screen geometry, timezone id, languages, hardware concurrency, device memory, permission states. Never collected: IP (server pseudonymises), geolocation, media device labels, battery, clipboard, page URL beyond origin + path hash, form values, cookies other than optional `__dk_rv` (off by default).

## 2. Transport and anti-tamper

### 2.1 Flow

```
page/snippet                              doorkeep server                     site backend
 <script src=/_dk/v1/dk.js data-sitekey>
 POST /v1/session {site_key, action} ---> create nonce (issued, ttl 120s)
 <--- {nonce, exp, seed, mod, now}
 collect stage 1 now, stage 2 idle
 on submit: POST /v1/submit {payload} --> consume nonce atomically, score
 <--- {status:"ok", token} | {status:"challenge", pow|visual}
 [challenge] POST /v1/challenge {nonce, solution} --> verify, mint token
 set hidden <input name="dk-response">
 form POST --------------------------------------------------------------> POST /v1/verify {secret, response}
                                                                        <--- {success, score, doorkeep:{...}}
```

The snippet always receives a token, including on `block`. The client never learns risk, outcome or reasons; only the site backend does via `/v1/verify`. This denies attackers a free oracle.

### 2.2 Serialisation and sending

JSON body via `fetch` POST with `Content-Type: text/plain;charset=UTF-8`, `credentials: 'omit'`, `keepalive: true` (CORS-simple, no preflight). `sendBeacon` only for the optional post-submit `/v1/supplement`. Integrations proxy `/_dk/*` on the site's own origin (removes CORS, defeats third-party-host blocking); direct cross-origin supported with `Access-Control-Allow-Origin` set to the registered origin. Payload 2-4 KB, no client compression.

### 2.3 Nonce design (anti-replay)

```
id 16 random bytes | site_id | origin | action | seed 8 bytes | issued_at | expires_at (120 s; 600 s once challenged)
state issued -> submitted -> challenged -> solved -> minted -> verified | expired
ip_hash HMAC(daily_key, ip/24 or /48) | ua_hash SHA-256(UA)[:8] | pow_salt | answer_hash HMAC(instance_key, id || answer)
```

Rules at `/v1/submit`:
1. `issued -> submitted` is one conditional write (SQL `UPDATE ... WHERE state='issued' AND expires_at>? RETURNING`; Redis Lua CAS). Second submit -> `REPLAY_NONCE`.
2. `Origin` (or `Referer` host) equals stored origin and is in the site's allowed origins; `Sec-Fetch-Site` consistent with deployment mode.
3. UA hash and IP /24 hash match the issue request.
4. Server elapsed within [40 ms, TTL]; client `t.s - t.i` within 1 s of it.
5. **Seed binding.** Seed is drawn into the canvas text and sets probe order. `canvas_seen(site_id, canvas_hash, seed_hash, ttl 24h)`: the same canvas hash with two different seeds is physically impossible -> `CANVAS_SEED_REPLAY` (near-block weight). This defeats "record one good payload, replay with fresh nonces".

Tokens are bound to site key, nonce id and origin; verify is single-use (`state = verified`; second verify -> `timeout-or-duplicate`).

### 2.4 Session response

```json
{ "nonce": "b64url16", "exp": 1760000000000, "seed": "b64url8", "now": 1759999880000,
  "mod": ["auto","fp","beh","env","audio","fonts","raf"], "deferMs": 500 }
```

### 2.5 What client-side measures cannot prevent

A bot driving a real browser produces a genuine payload. The snippet is an evidence collector, not a trust anchor. Server-side responsibilities: cross-layer consistency (UA header vs `navigator.userAgent` vs `Sec-CH-UA` vs engine class vs TLS class vs h2 class), velocity and distribution, timing truth, network reputation, nonce lifecycle and seed binding. Snippet obfuscation, polymorphism and a JS VM are non-goals.

### 2.6 Result token format

| Option | Pros | Cons |
|---|---|---|
| JWT | Ubiquitous | Alg-agility footguns; claims readable by client (evasion oracle) |
| PASETO v4.local | Versioned, no alg negotiation, XChaCha20-Poly1305 so claims are opaque, implicit assertions bind site key | Larger tokens (~300 B); fewer libs elsewhere (irrelevant) |
| Custom HMAC | Smallest | No test vectors; reviewers distrust it |

**Recommendation: PASETO v4.local** via `aidantwoods.dev/go-paseto`, key id in footer, site key as implicit assertion, per-instance 32-byte `DOORKEEP_TOKEN_KEY` with two-key rotation.

Claims: `iss, iat, exp, jti (nonce id), sid, org, act, eid, risk, out, rc[], ch (pow|visual|none), ip24, v`.

Verify: decrypt, check `exp`, `sid` matches secret's site, compare `org`/`act` to `expected_hostname`/`expected_action`, compare `ip24` to `remoteip` if `strict_ip`, transition nonce to `verified`. If the nonce row is gone the token is rejected even though it decrypts.

## 3. Server-side signals

### 3.1 TLS fingerprint

**JA4** (JA3 breaks on Chrome's randomised extension order). When doorkeep terminates TLS (recommended; Docker default with certmagic ACME): `peekConn` reads the first TLS record, parses the ClientHello with `utls.UnmarshalClientHello`, computes JA4, stores by `net.Conn` in `sync.Map`, replays bytes to `crypto/tls`; handler reads via `Server.ConnContext`. Behind a proxy: accept `Doorkeep-TLS: ja4=...` only from `trusted_proxies` CIDRs; recipes for HAProxy (`ssl_fc_*_bin` + `dk-ja4` converter), Nginx ja4 module, Cloudflare transform rule; Caddy documented as degraded. Absent -> `TLS_UNAVAILABLE` informational, model treats as missing.

### 3.2 HTTP/2 fingerprint

Akamai-style: SETTINGS list, WINDOW_UPDATE, PRIORITY, pseudo-header order (Chrome `:method,:authority,:scheme,:path`; Firefox `:method,:path,:authority,:scheme`; Go `:authority,:method,:path,:scheme`). Same `peekConn` after TLS when ALPN = h2, passive parse with `x/net/http2` Framer + hpack on a buffered copy. HTTP/1.1 header order captured from the raw first block (works behind Nginx). Rules: `h2_class` vs `ua_family`; Chrome UA over HTTP/1.1 when h2 was offered.

### 3.3 Header consistency

Parse with `github.com/mileusna/useragent`. Expectations: Chromium >= 89 sends `Sec-CH-UA*` agreeing with UA and payload; Firefox/Safari must not; all modern browsers send `Sec-Fetch-*`; `Accept-Language` primary tag in `navigator.languages`; `Accept-Encoding` includes `zstd` for Chrome >= 123; `Accept: */*` for fetch POST; no `Connection: keep-alive` on h2. Codes: `UA_CH_MISSING`, `UA_CH_MISMATCH`, `FETCH_METADATA_MISSING`, `UA_ENGINE_MISMATCH`, `UA_TLS_MISMATCH`, `UA_H2_MISMATCH`, `UA_HTTP1_ON_H2`.

### 3.4 IP intelligence (freely redistributable only)

`doorkeep ipdata update` (weekly cron in container) builds `ipdata.bin` (serialised `bart` table) and hot-reloads.

|---|---|---|

| ASN fallback | iptoasn.com `ip2asn-combined.tsv` | PDDL 1.0 |
| Alternative | ipinfo free country+ASN mmdb | CC BY-SA 4.0 |

| Tor exits | torbulkexitlist, Onionoo (hourly) | Tor Project |
| Known-bad | Spamhaus DROP/EDROP (runtime download, not bundled) | free use |

### 3.5 Rate and velocity

In-process sliding windows (60 one-second buckets per key, 1 h expiry); cluster mode uses Redis Lua GCRA.

| Key | Features (1 min / 10 min / 1 h) | Why |
|---|---|---|
| `ip` | issues, submits, verify failures, challenge failures | rate limiting |
| `ip24` | same + distinct `fp_hash` | NAT vs farm |
| `fp_hash` | submits, distinct `ip24`, distinct `asn` | residential-proxy tell |
| `canvas_hash` | distinct `ua_family`, distinct `asn` | same renderer, many claimed browsers |
| `site`, `site+action` | submits, challenge rate, block rate vs 7-day baseline | attack detection, adaptive PoW |
| `asn` per site | submits vs baseline | ASN surges |

Hard limits before scoring: `/v1/session` 60/min per IP, 600/min per /24 (configurable); 429 treated by integrations as `challenge`.

### 3.6 Timing anomalies

Server vs client elapsed mismatch; clock skew > 5 min; inter-submit regularity per `fp_hash`/`ip24` (CV < 0.05 over >= 10 events); local time-of-day as weak model feature; collection duration implausibly short for modules requested.

## 4. Scoring engine

### 4.1 Pipeline

```
request -> net signals -> payload normalisation -> feature vector (~70)
 -> hard lists (allow/deny) -> rules layer -> model layer -> blend -> risk 0..100
 -> per-site thresholds -> outcome {allow, challenge, block} -> reasons[] + shadow[]
```

### 4.2 Feature vector

Flat `map[string]float64`; `internal/scoring/features.go` is the single source of truth and generates docs. Booleans, bucket ordinals, bounded floats. Missing = NaN = "unknown" to both layers (neutral-when-absent enforced mechanically).

### 4.3 Rules layer

Rules are YAML data evaluated with `github.com/expr-lang/expr`; built-ins embedded, per-site overrides via admin API.

```yaml
- id: AUTOMATION_WEBDRIVER
  when: "auto.wd == 1"
  weight: 45
  mode: enforce          # enforce | shadow | off
- id: CANVAS_SEED_REPLAY
  when: "net.canvas_seed_conflict"
  weight: 90
- id: UA_ENGINE_MISMATCH
  when: "fp.ua_family in ['firefox','safari'] && auto.eng == 'v8'"
  weight: 60
  unless: "prof.rfp"
- id: FP_MULTI_ASN
  when: "vel.fp_distinct_asn_1h >= 5"
  weight: 50
- id: NO_INTERACTION_FAST_SUBMIT
  when: "beh.total_events == 0 && t.elapsed_s < 2 && action in site.interactive_actions"
  weight: 25
- id: PROFILE_RFP
  when: "prof.rfp"
  weight: 0
  informational: true
- id: GOOD_CROWD_SIGNAL
  when: "beh.ptr_samples > 30 && beh.ptr_straightness < 0.9 && beh.ptr_interval_cv > 0.2"
  weight: -20
```

Rules risk = `clamp(sum(weights of fired enforce rules), 0, 100)` (linear so operators can predict effects). Lists per site with expiry and note: `allow` (IP/CIDR, ASN, country, fp_hash, UA regex, verified crawler) -> risk 0; `deny` -> risk 100; `always_challenge`.

### 4.4 Model layer

**HBOS (histogram-based outlier score) as v1 unsupervised scorer, online logistic regression once labels exist.** Isolation forest rejected for v1: unexplainable single number, batch retraining. HBOS gives per-feature contributions -> `MODEL_ANOMALY:<feature>`.

```go
type Scorer interface {
    Score(ctx context.Context, f Features) (risk float64, contrib []Contribution, err error)
    Observe(f Features, label *Label)
    Snapshot() ([]byte, error)
}
```

HBOS: one histogram per feature, per site and global, exponential decay half-life 7 days; blend `p = (n_site*p_site + k*p_global)/(n_site+k)`, k = 1000 until 5000 site events; cold-start priors embedded from the CI corpus; map to 0-100 by the site's rolling 7-day 99th percentile.

Supervised: L2 logistic regression over features + HBOS score, online SGD (~150 lines, no dependency). Labels: dashboard clicks, `POST /v1/report`, challenge outcomes as weak labels. Auto-created in shadow after >= 200 labels with >= 50 per class; dashboard shows shadow precision/recall; operator promotes. Contributions exposed as `MODEL_LR:<feature>`.

Blend: `risk = clamp(rules + model_weight * model_risk)`, `model_weight` 0.3 (HBOS) / 0.5 (promoted LR). Model never overrides allow-lists and never moves `allow` to `block` (cap +40).

### 4.5 Score range, outcomes, thresholds

`risk` 0-100. `allow` if `< t_challenge` (35), `challenge` if `< t_block` (75), else `block`. Per site and per action overrides. Site modes: `enforce`, `monitor` (always allow tokens, record would-be), `challenge_only`. After a solved challenge, risk is reduced by a credit (`pow: 20`, `visual: 45`) and re-banded.

### 4.6 Shadow mode

Every rule, list entry and model has `mode`. Shadow contributions stored in `shadow[]`. Dashboard "Rule lab": fire count, overlap with enforced outcomes, outcome shift if promoted, precision against labels. Rulesets versioned with `active_version` per site; promote/rollback atomically via admin API, audited.

## 5. Challenge fallback

### 5.1 Proof-of-work

SHA-256 with many small sub-puzzles (tight solve-time concentration; Argon2id rejected as 10-50x slower on low-end phones for no benefit since PoW is a rate limiter).

Issue: `{ "status": "challenge", "kind": "pow", "pow": { "salt": "b64url16", "bits": 12, "n": 10, "exp": ... } }`. Solve in Web Workers (inline blob, up to `min(hardwareConcurrency, 4)`): for each `i`, find smallest `x` such that `SHA-256(nonce || salt || uint32(i) || uint32(x))` has `bits` leading zeros. `crypto.subtle` batched, bundled JS SHA-256 fallback, optional 2 KB WASM. Server verifies with `n` hashes.

| Risk band | bits | n | Expected hashes | Low-end phone, 2 workers |
|---|---|---|---|---|
| 35-50 | 12 | 10 | 41k | ~0.25 s |
| 50-62 | 12 | 24 | 98k | ~0.5 s |
| 62-75 or site under attack | 13 | 24 | 197k | ~1.0 s |
| mobile cap | never above 200k expected | | | |
| desktop under heavy attack | 14 | 32 | 524k | ~0.3 s desktop |

Per-site `pow.max_expected_hashes` and adaptive multiplier from site submit rate vs baseline. PoW always offered first (no accessibility cost).

### 5.2 Accessible visual and audio alternative

Honest framing: solvable by multimodal models for a fraction of a cent; it is a human path and a cost raiser, not a security boundary. Documented as such.

- Visual: 5 characters from an unambiguous alphabet rendered as SVG with 3 OFL fonts, per-glyph affine distortion, baseline wobble, stroke jitter, two Bezier strike-throughs, noise rectangles; seeded by nonce; answer stored only as `HMAC(instance_key, nonce_id || answer)`. Plain text input, `aria-describedby`, keyboard operable, forced-colours safe.
- Audio: same characters from espeak-ng clips generated at build time (3 voices, 2 speeds), concatenated with random gaps, pitch shift +-5%, brown noise; Ogg/Opus and WAV; replay and slower controls.
- `accessibility_url` escape hatch per site. 3 attempts per nonce, then burned (token says `block`); TTL extended to 10 minutes on challenge issue.

### 5.3 Binding to the nonce

`pow_salt` and `answer_hash` written at `submitted -> challenged`; PoW preimage includes nonce id; solution endpoint performs `challenged -> solved` as one conditional write; minting moves `solved -> minted`. Escalation `pow -> visual` uses sub-states `challenged_pow`, `challenged_visual` within the same nonce.

## 6. Storage and privacy

### 6.1 What is stored

| Table | Contents | Retention |
|---|---|---|
| `sites`, `site_keys`, `site_settings` | config; secrets as SHA-256 | until deleted |
| `nonces` | section 2.3 | `expires_at + 1 h` |
| `events` | id, site_id, ts, action, risk, outcome, reasons, shadow, features (bucketed CBOR), fp_hash (16 B), ip24_hash (16 B), asn, asn_class, country, ua_family, ua_major, os_family, tls_class, h2_class, challenge_kind, challenge_ok, verified_at, label, label_source | 30 days (1-90) |
| `canvas_seen` | site_id, canvas_hash, seed_hash | 24 h |
| `aggregates_hourly` | per site/hour counts by outcome, reason, country, asn_class, ua_family; risk histogram; challenge solve rates; collection time p50/p95 | 13 months |
| `lists`, `rulesets`, `rules` | operator config | until deleted |
| `model_state` | HBOS histograms, LR weights | nightly snapshots, 7 kept |
| `training_examples` | features + label + ts (no hashes) | 180 days |
| `admin_users`, `admin_sessions`, `audit_log` | argon2id; every config change with actor and diff | audit 13 months |

Raw IP only in memory and rate counters (TTL <= 1 h); never on disk or in logs (slog redaction filter). Raw UA, WebGL strings, tz, languages exist only during request handling.

### 6.2 Pseudonymisation keys

- `fp_hash = HMAC-SHA256(site_pepper_month, canvas_hash || gl_hash || font_mask || screen_bucket || tz || langs || ua_family || os_family || hc_bucket)[:16]`, `site_pepper_month = HKDF(instance_secret, "fp" || site_id || YYYY-MM)`. Same device yields different hashes per site and per month.
- `ip24_hash = HMAC-SHA256(HKDF(instance_secret, "ip" || YYYY-MM-DD), prefix)` with /24 (v4) or /48 (v6). Day-scoped.
- `instance_secret` in `DOORKEEP_SECRET` (32 bytes); rotation is a hard cut of all linkage.

### 6.3 What the dashboard can show

Allowed: aggregates, event list with pseudonymous columns, drill-down by `fp_hash` within one site and one month, "today's events from IP x" (hashed with today's key), rule lab, labels, retention and data-map pages. Not offered (enforced in the admin API): cross-site queries by any identifier, IP history beyond today, raw signals, exports keyed by `fp_hash`.

### 6.4 Data map (`docs/privacy/data-map.md`, rendered at `/admin/privacy`)

| Data item | Form at rest | Purpose | Retention | GDPR | DPDP |
|---|---|---|---|---|---|
| IP address | day-keyed /24 or /48 HMAC; ASN; country | velocity, reputation | 30 d events, 1 h counters | personal data; Art. 6(1)(f), Recital 49 | personal data processed by the site as Data Fiduciary; operator usually same entity or Processor; self-hosting keeps data in-country |

Also: no cookies by default; no transfers (self-hosted); DSAR via site's `event_id` mapping and `DELETE /admin/v1/events/{id}`; breach scope pseudonymous; DPDP Rules 72-hour Board report supported by exporting the data map and retention state.

### 6.5 Database choice

**SQLite via `modernc.org/sqlite` default (CGO-free static binary); Postgres optional (`pgx/v5`); no BoltDB** (dashboard needs SQL aggregation). WAL, `synchronous=NORMAL`, `busy_timeout=5000`, one writer goroutine batching events every 100 ms. Migrations: goose embedded, two dialect directories; sqlc per dialect. Cluster: Postgres + Redis (nonce `SET NX PX` + Lua CAS, Lua GCRA, `canvas_seen`, pub/sub for config and model invalidation). Multi-node without Redis unsupported in v1 (documented). TLS/h2 fingerprinting in clusters needs each node to terminate TLS behind an L4 balancer with PROXY protocol v2 (`go-proxyproto`).

## 8. Integration surface

Every integration needs: the snippet (proxied `/_dk/v1/dk.js` or direct), field name `dk-response`, and the verify call. Shared verify clients: `pkg/verify` (Go), `@doorkeep/verify` (Node), `doorkeep/verify` (PHP), each ~80 lines with timeouts, `expected_action`, `fail_mode: open|closed`.

### 8.1 Next.js (`@doorkeep/next`)
Client `<Doorkeep action="signup" />`, `useDoorkeep()` -> `execute(action)`; server `verifyDoorkeep(input, opts)` for Server Actions and Route Handlers reading `DOORKEEP_URL`, `DOORKEEP_SITE_KEY`, `DOORKEEP_SECRET`; `withDoorkeepProxy(nextConfig)` adds the `/_dk/:path*` rewrite; `doorkeepMiddleware({ protect })` uses edge-mode cookie via `/v1/auth`. ### 8.2 WordPress
Settings page (URL, site key, secret, fail mode, forms, compat field names). Hooks: `login_form`, `register_form`, `lostpassword_form`, `comment_form_after_fields` (render); `wp_authenticate_user`, `registration_errors`, `lostpassword_post`, `preprocess_comment` (verify); WooCommerce checkout; CF7, WPForms, Gravity Forms. `wp_remote_post` 3 s timeout. ### 8.3 Nginx and Caddy
**auth_request / forward_auth sidecar, not a plugin** (no rebuilds; pattern Anubis and Authelia already taught this audience). Protect expensive paths, not the whole site. `GET /v1/auth` checks `__dk_edge` cookie (PASETO v4.local, 1 h, bound to site, UA family, optionally ip24); `200` with `X-Doorkeep-Risk`, `X-Doorkeep-Reasons`, `X-Doorkeep-Fp`, or `401` -> redirect to `/_dk/challenge?rd=`. Verified crawlers and allow-list pass without cookie. API paths can return `401` JSON. Caddy: `/v1/auth` returns `302` itself when `Accept` is HTML and `X-Doorkeep-Mode: redirect` is set.

```nginx
location /_dk/ { proxy_pass http://doorkeep:8080/; }
location /search {
  auth_request /_dk_auth;
  error_page 401 = @dk_challenge;
  proxy_pass http://app;
}
location = /_dk_auth { internal; proxy_pass http://doorkeep:8080/v1/auth; proxy_pass_request_body off; proxy_set_header Content-Length ""; proxy_set_header X-Original-URI $request_uri; }
location @dk_challenge { return 302 /_dk/challenge?rd=$request_uri; }
```

```caddyfile
handle_path /_dk/* { reverse_proxy doorkeep:8080 }
@protected path /search* /api/*
handle @protected {
  forward_auth doorkeep:8080 { uri /v1/auth; copy_headers X-Doorkeep-Risk X-Doorkeep-Reasons }
  reverse_proxy app:3000
}
```

## 9. Threat model

| Attack | v1 handles | Cannot |
|---|---|---|
| Replay of payload or token | one-time nonce, atomic transitions, origin/UA/ip24 binding, TTL, canvas seed binding, single-use verify | replay from the same machine re-running the real snippet (not a replay) |
| Payload forgery | cross-layer consistency, timing truth, seed binding, velocity, HBOS "too perfect" | real browser per request; cost pushed to velocity/network |
| Headless with stealth (puppeteer-extra-stealth, playwright-extra, patchright, Camoufox, Nodriver) | realm checks, CDP artefacts, software GPU and font/OS mismatch, behaviour impossibility, TLS/h2 class, velocity, PoW and visual cost | well-configured headed Chrome with GPU and replayed human input; detection rests on volume |
| Residential proxies | `fp_hash` across many ASNs/countries, tz vs IP drift | identify residential IPs from free data |
| Distributed low-rate | baseline shift alerts, clustering, HBOS, shadow rules, feedback | no cross-instance intelligence in v1 |
| Snippet blocked / no JS | same-origin delivery, hosted interstitial, explicit `fail_mode` | score a client that never runs JS |
| Verify oracle abuse | client never sees risk/outcome; blocked tokens look identical | inference from site behaviour |
| Brute force against doorkeep | rate limits, 3 challenge attempts, argon2id + lockout, constant-time compares | volumetric DDoS |
| Operator turning it into a tracker | per-site per-month peppers, day-scoped IP hashes, no raw storage, admin API refuses cross-site queries | a patched fork |

Non-goals v1: volumetric DDoS; WAF; ATO beyond bot signal; credential-stuffing lists; snippet obfuscation/VM; shared reputation network; native mobile SDKs; Private Access Tokens; TLS fingerprinting behind non-forwarding proxies; paid IP intelligence; multi-region active-active; CAPTCHA strength against vision models.

## 11. Implementation notes: where the build departs from this design

Recorded so maintainers know which differences are deliberate.

- **PASETO v4.local is implemented in-tree** (`internal/token`) on
  golang.org/x/crypto instead of `aidantwoods.dev/go-paseto`, whose vanity
  domain did not resolve. It passes every official v4.local test vector; the
  vectors caught a malleability bug (non-canonical base64), fixed with
  strict decoding.
- **JA4 uses an in-tree ClientHello parser** fed by a recording net.Conn,
  not utls. Nothing is replayed, so ALPN and HTTP/2 negotiation are
  untouched. Validated against real Chromium (published cipher hash
  `8daaf6152771`).
- **Firefox 157 shares Chromium's cipher list**, so TLS separates browsers
  from libraries, and the HTTP/2 fingerprint separates browsers.
- **Two canvas hashes**: a seeded one binds the payload to its nonce (replay
  detection); a static one is the stable device component. With only the
  seeded hash, a real device would get a new fingerprint each session.
- **Floor rules**: proof signals (webdriver true, automation globals,
  HeadlessChrome, canvas replay, DROP list, sub-40 ms submit) set a minimum
  risk that negative evidence cannot reduce and no challenge can clear.
  Found when a replayed payload's replayed "human behaviour" offset its own
  replay signal, and when headless Firefox passed by solving the PoW.
- **Human-evidence rules do not apply when a device contradicts itself**
  (fonts, GPU, client hints, TLS or HTTP/2 vs the claimed browser), because
  behaviour can be synthesised. Found with the stealth plugin.
- **Proof of work clears only the lower half of the challenge band** (risk
  below threshold + 20); above that the same nonce escalates to the visual
  challenge.
- **The CDP console probe is dead on current Chromium**; kept at weight 25
  for older builds and tracked as a known miss.
- **The visual challenge renders a bitmap font into a PNG** (no glyph text
  in the DOM) instead of SVG with bundled OFL fonts. Audio clips are
  generated at build time with espeak-ng in Docker.
- **HBOS trains only on traffic allowed at low risk** and has no opinion
  under 200 observations, instead of shipping corpus priors.
- **The SQLite and Postgres stores share one implementation** (`sqlstore`)
  rather than separate sqlc-generated packages.
- **Redis velocity uses HyperLogLog** per bucket for distinct counts instead
  of Lua GCRA scripts; session rate limiting reads the same counters.
- **The velocity tracker stores buckets sparsely**; the fixed ring cost ~7 KB
  per key and was found by the load test.
