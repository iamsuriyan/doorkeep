# Open-source tooling gaps created by the AI coding-agent era (state as of 2026-10-22)

Scope: Claude Code, Codex CLI, Cursor, Copilot agents, MCP servers, agent skills/plugins. Evidence gathered 2026-10-22 from GitHub issue trackers (via the GitHub API, reaction counts are thumbs-up at query time), MCP spec discussions, Hacker News (Algolia API, points/comments at query time), vendor docs, and 2026 reports from Trail of Bits, OWASP, CSA and OpenSSF. Excluded by assignment: generic MCP/skill scanners and inbound vulnerability-report triage.

Method notes: GitHub full-text search matches issue bodies, so I filtered by title relevance; "open/closed" states and counts are as returned on 2026-10-22. Repo health numbers (stars, last push, license, top contributors) are from the GitHub API on the same day. Where I could not fetch a primary source I say so.

## Key question 1: Which security/permissions/audit/secrets/sandbox/cost/policy requests in the claude-code, codex and MCP trackers have the most reactions and remain open or were closed without a real fix?

### Takeaway
The highest-reaction security-adjacent requests are (a) excluding sensitive files from the agent (codex #2847, +473, closed only after ten months with a beta that commenters report is inconsistently enforced), (b) permission-rule matching that actually enforces allow/deny on compound shell commands (claude-code #16561 +176, #28240 +209, #30519 +80 — the last one documents "30+ open issues" and users rebuilding enforcement in hooks), (c) revert/undo of agent edits (codex #9203 +487, #11626 +228), and (d) auditability of what sub-agents were told (codex #28058 +137, open). Secrets handling in Claude Code has a documented cluster of 18+ open requests with "zero shipped" as of Aug 2026 (#90301). MCP spec security proposals (permission spec, signed manifests, TBOM, enforcement mode, execution receipts) drew long comment threads but every Discussion thread was closed on 2026-09-25 when the repo limited Discussions to meeting notes, with none accepted as a SEP.

### Inferences
- The permission-matching cluster is the single most-reacted security pain point in claude-code, and it keeps regressing (#91650 filed Sept 2026 after #16561 closed in Aug 2026), so a vendor-independent, testable policy layer has durable demand.
- Codex closing #2847 with a vendor-specific beta, plus the explicit asks for a tool-agnostic `.agentignore`, suggests a cross-tool exclusion standard with conformance tests is wanted but nobody owns it.
- Secrets handling has many low-reaction but highly detailed issues (#90301, #95680) rather than one viral issue; demand is real but diffuse, and part of it (credential brokering) is now crowded (see KQ2).
- MCP governance proposals are being pushed out of the spec repo (Discussions closed 2026-09-25) into "interest groups", which makes a de-facto OSS implementation more valuable than waiting for a SEP.

## Key question 2: What do developers say they lack for operating agents safely in teams (audit trails, policy enforcement, secret leakage, egress control, approvals, reproducible runs, session diffs), and what does the vendor tooling already cover?

### Takeaway
Vendors now ship pieces: Claude Code has an OS-level Bash sandbox with a domain-allowlist proxy and credential deny/mask, OpenTelemetry export, and `/rewind`; Codex has permission profiles; Copilot signs agent commits and GitHub exposes enterprise agentic audit logs. The documented holes are: the sandbox "covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it"; OTEL variables are not passed to subprocesses, hooks or MCP servers; there is "no built-in credential deny list"; transcripts can be silently deleted; sub-agent instructions are encrypted in Codex; and nothing cross-tool normalizes what an agent did across Claude Code, Codex and Cursor.

### Cited Findings
- Claude Code sandbox docs: "The sandbox covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it." "On native Windows, Claude Code runs commands unsandboxed." "The built-in proxy enforces the allowlist based on the requested hostname and, by default, does not terminate or inspect TLS traffic." "Tools that ignore the proxy variables: plain ssh, most database drivers, and similar tools can't connect, even to an allowed host." "An allow rule that matches a command also approves an unsandboxed retry of it, so the command can run outside the sandbox with no prompt." "There is no built-in credential deny list, so only the files and variables you list are restricted." "`sandbox.credentials` affects sandboxed Bash commands only." Credential masking: "the sandbox proxy substitutes the real value on outbound requests to hosts you allow" and requires `network.tlsTerminate` — [Source](https://code.claude.com/docs/en/sandboxing)
- Claude Code monitoring docs: events exported include user_prompt, assistant_response, api_request, tool_decision, tool_result, mcp_server_connection; "Spans redact user prompt text, tool input details, and tool content by default" (opt-in via OTEL_LOG_USER_PROMPTS / OTEL_LOG_TOOL_DETAILS / OTEL_LOG_TOOL_CONTENT / OTEL_LOG_ASSISTANT_RESPONSES); "Claude Code doesn't pass OTEL_* environment variables to the subprocesses it spawns, including the Bash tool, hooks, MCP servers, and language servers." — [Source](https://code.claude.com/docs/en/monitoring-usage)

## Key question 3: MCP server and agent-skill supply chain — beyond scanners, what is missing (signing, provenance, lockfiles, permission manifests, trust registry, runtime sandbox per server), and what do the MCP spec discussions and OpenSSF/OWASP/CSA/Trail of Bits say is unsolved?

### Takeaway
Institutions converge on the same unsolved list: hash-pinning/lockfiles for tool definitions and skills, signed manifests with drift detection, provenance that binds a published server/skill to its source, least-privilege capability manifests, and runtime evidence of what a tool actually did. Every open-source attempt at these is a single-maintainer repo with 0-9 stars (mcptrust, skills-lock, skillledger, mcp-signed-manifests, CTMS, me-guard, Haldir), while scanners (SkillSpector 20,856 stars, snyk/agent-scan 3,161) are well-funded. Signing alone is acknowledged as insufficient ("Signing does not prove a skill is safe"; Shai-Hulud packages carried valid SLSA L3 attestations).

## Key question 4: Agent-generated code review and verification — what is missing in open source for proving an AI-written change is safe (tests-as-evidence, session SBOM, SLSA-style attestations for agent commits)?

### Takeaway
Open source covers attribution (git-ai, line-level, 2,879 stars) and vendors cover identity (Copilot signed commits), but nothing widely used binds a commit to verifiable evidence of how it was produced: transcript hash, model, tools called, tests executed and their results, and policy decisions. The pieces exist (in-toto attestation framework, Sigstore/gitsign, draft in-toto agent predicates, IETF EAT-for-agents draft) and the only agent-specific implementations are 0-star repos.

### Cited Findings
- Copilot cloud agent commit signing (2026-04-03) proves agent identity and integrity only — [Source](https://github.blog/changelog/2026-04-03-copilot-cloud-agent-signs-its-commits/). Commentary: "a signed commit from Copilot cloud agent can contain logic errors ... the agent writes plausible code, but plausible isn't correct" — [Source](https://www.tenki.cloud/blog/copilot-commit-signing-code-review)
- git-ai: "On commit, Git AI stores line-level attribution data in Git Notes, linking each line of AI-generated code to the agent, model, and session that created it"; "The teams version adds a secure prompt store" — [Source](https://github.com/git-ai-project/git-ai)
- A DZone piece on verifiable provenance for AI code argues a minimal record should bind "the generated artifact to the model provider, model identifier and revision, agent identity and version, prompt digest, context digests, execution trace, repository commit, intent digest, timestamp, and approving human or service identity" — [Source](https://dzone.com/articles/verifiable-provenance-ai-code)
- In-toto-based agent attestation predicates ("v1 in-toto Statement payloads ... describe AI-agent runtime behavior and session-level agent actions, complementary to SLSA provenance") are specified in occasiolabs/occasio — [Source](https://raw.githubusercontent.com/occasiolabs/occasio/HEAD/spec/agent-attestation/v1/README.md); IETF draft-messous-eat-ai-01 (Feb 2026) defines Entity Attestation Tokens for AI agents with an `ai-sbom-ref` claim — [Source](https://mirror.apps.cam.ac.uk/pub/doc/internet-drafts/draft-messous-eat-ai-01.html); fast.io "AI Agent Output Attestation" guide — [Source](https://www.fast.io/resources/ai-agent-output-attestation.md)
- arXiv 2609.28216 "From Agent Output to Authorized Transition" (Sept 2026) frames authorization of agent-produced changes as a transition problem — [Source](https://arxiv.org/pdf/2609.28216)
- MCP Discussion #3215 (execution receipts) and issue #3350 "SEP submission: Tool Outcome Attestation extension" (closed, 2026-09-06) show the same need at tool-call level — [Source](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/3350)
- Demand signal from users: claude-code #59248 comment that transcripts "serve as a proof of work, justifying the spend" and may be needed "to audit the user to confirm how the tokens were spent" — [Source](https://github.com/anthropics/claude-code/issues/59248)
- Existing OSS: David-Wu1119/aiattest ("Signed AI run and agent provenance attestations") — 0 stars, MIT — [Source](https://github.com/David-Wu1119/aiattest); semanticash/cli (AI code provenance) — 5 stars — [Source](https://github.com/semanticash/cli); AgenTag (behavioral fingerprinting of which agent wrote a PR, F1 0.96) is research, not provenance — [Source](https://codex.danielvaughan.com/2026/08/13/agentag-attribution-ai-coding-agents-behavioral-fingerprints-codex-cli-commit-attribution-pr-governance/)
- Counter-evidence that signatures are not safety: Shai-Hulud malicious packages carried valid SLSA L3 attestations (CSA note above).

### Inferences
- The buildable gap is a `git`-native "agent change attestation" tool: emit an in-toto statement per agent commit (session transcript digest, model, tools/MCP servers used, tests run and exit codes, policy decisions from hooks), sign with Sigstore/gitsign, verify in a GitHub Action, and surface it in PR review. git-ai could be a data source rather than a competitor.
- User-level demand is weaker than for KQ1 items; demand is institutional (compliance, EU AI Act logging obligations from 2026-08-02 per Maxim/obot blogs) and from maintainers of large repos drowning in agent PRs. Mark as medium-risk.

### Gaps
- I found no GitHub issue in claude-code or codex explicitly requesting SLSA-style attestations; evidence is from standards drafts and blogs.
- I did not verify the EU AI Act logging claims against the regulation text.

## Key question 6: Which 8-15 gaps are candidates for a solo security/web developer to open source in a few months?

### Takeaway
Twelve candidates below, ordered by (demand evidence x absence of healthy OSS x buildability by 1-3 people). The top six are: cross-tool sensitive-file exclusion kit, agent-permission policy compiler with a bypass corpus, local cross-agent action ledger with change manifests, transcript secret scrubber, MCP/skill lockfile-and-drift CI action, and agent commit attestation.

### Cited Findings
Each entry: demand evidence (cited above), what exists, shortcoming, buildability. "Inference" marks my judgement.

1. Cross-tool sensitive-file exclusion standard + enforcer (`.agentignore` conformance kit). Exists: claudeignore (6 stars, needs sandbox), garogarabed12/agentignore (6 stars, spec only), FUSE/Rust toys (2-3 stars). Demand: claude-code #95680 ("no way to find or scrub them"; Cloakroom maintainer: "still open"), #90301 (18 open requests), #29910 (+37), #20966, #18653 (+17). Exists: Cloakroom (4 stars, masks tool results only), OneCLI/agent-vault (brokers; do not touch stored transcripts), vendor credential `deny`/`mask` (sandboxed Bash only; "no built-in credential deny list"). Shortcoming: no gitleaks-style scanner with rules for agent stores (JSONL transcripts, tool_result blocks, rollout files, OTel exports), no in-place scrub that preserves resumability, no report of which secrets already reached the API. Buildability: high (inference); reuse gitleaks/trufflehog rule sets. — [Source](https://github.com/anthropics/claude-code/issues/95680), [Source](https://code.claude.com/docs/en/sandboxing)

Demand: MCP #2913, #2189, #2444, registry #82, agentskills #46/#110, codex #18115 (+68, reproducible team plugin setup), OWASP AST07/AST02, CSA "verify hashes at load time", Mend "no lockfile for prose". ### Inferences
- Items 1-5 share plumbing (hook adapters for Claude Code/Codex, a shell parser, a normalized event schema); a solo developer could ship 1 and 4 first (weeks each), then 3 and 2, and reach 5 and 6 on the same code base.
